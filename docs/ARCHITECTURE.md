# Архитектура · публичный портал, аккаунты и кабинеты

## Решение

Модульный монолит Next.js App Router + TypeScript + Tailwind CSS 4. Отдельные клиентские компоненты только там, где требуется состояние: меню, поиск, каталог, расписание, формы. Контентные страницы — Server Components. Сейчас интерфейс не зависит от доступности PostgreSQL. Встроенные данные — временный адаптер демонстрации, не источник истины.

Обычный build создаёт standalone Node.js 24.7+ приложение для Docker/Linux с собственным email/password auth и PostgreSQL. `build:public` собирает отдельный статический предпросмотр без API; Sites и автономный HTML показывают публичный интерфейс и демонстрационный кабинет. Перед эксплуатацией с реальными персональными данными нужны рабочий сервер, SMTP, приёмка и эксплуатационные проверки. Реализованный протокол авторизации и запуск описаны в [ACCOUNTS.md](ACCOUNTS.md).

## Данные

Prisma 7, PostgreSQL, UUID; служебное время timestamptz, учебные даты date, время пары time в Europe/Moscow. Course — запуск дисциплины в учебном году и семестре. CourseTeacher/CourseGroup поддерживают несколько преподавателей и групп. StudentGroupMembership сохраняет историю переводов. Предусмотрены задания, попытки сдачи, тесты и ответы, зачётная книжка, CMS, файлы, ДПО, уведомления, заявки принадлежности, роли, сессии, одноразовые токены и аудит.

Группы имеют самостоятельную таблицу и seed из опубликованных расписаний. Регистрация загружает активные Group через серверный API; код формы не содержит списка групп. CRUD учебных справочников входит в будущую полную админку.

SQL-миграция содержит ограничения интервалов и значений, уникальную активную группу студента, регистронезависимую уникальность email и одну обложку новости. Схема не заменяет объектные проверки: принадлежность ответа вопросу того же теста, балл не больше maxScore, доступ студента к курсу, назначение преподавателя и отсутствие пересечений расписания проверяются транзакционно в будущих сервисах. Опубликованный тест с попытками неизменяем, новая редакция — новый Test.

## RBAC

GUEST — отсутствие сессии. Поддерживаются STUDENT, TEACHER, EDITOR, EDUCATION_ADMIN, ADMIN, SUPER_ADMIN. Роли множественные; нет неограниченной иерархии. Общая матрица будущих модулей находится в src/server/policies/rbac.ts. Текущие auth handlers проверяют серверную сессию, статус, подтверждённую почту и конкретный объект; административные handlers требуют ADMIN/SUPER_ADMIN.

- STUDENT — свои результаты/работы и назначенные курсы.
- TEACHER — курсы через CourseTeacher и связанные группы.
- EDITOR — публичный контент без персональных данных.
- EDUCATION_ADMIN — учебные справочники и расписание.
- ADMIN — управление пользователями и обычные административные операции.
- SUPER_ADMIN — особо привилегированные назначения.

## Авторизация, этап 2

Выбор роли в анкете — requestedRole, не действующая роль. Реализованы подтверждение email и отдельная сверка принадлежности администратором. Одноразовая activation link подтверждает только почту. Назначение STUDENT/TEACHER, создание профиля, привязка группы и аудит выполняются в транзакции проверки заявки. Первый ADMIN назначается только явной операторской CLI-командой.

Пароли: Argon2id, параметры измеряются на сервере; никаких предсказуемых паролей и plaintext. Сессии серверные, отзываемые, cookie HttpOnly/Secure/SameSite=Lax без общего Domain с прежним Moodle. Для Server Actions — проверка Origin/Host; для иных cookie-auth endpoint — CSRF/Origin защита. Никаких мутаций GET. Rate limiting отдельно для входа, reset и активации; нейтральные сообщения против перебора email.

src/server/auth реализован; входные точки импортируют server-only. UI получает минимальные DTO, не модель User целиком. AuditLog не содержит паролей, токенов и полных анкет. Для будущего редактора и загрузки материалов потребуются очистка HTML, приватный S3, проверка MIME/размера/архивов, карантин. Перед production нужна отдельная append-only роль для аудита.

## Внешние ресурсы

Фотографии сохраняются локально; авторство на /credits. Карта загружается с Google Maps только на странице контактов; есть независимая ссылка на Яндекс Карты. Внешние переходы к текущим системам явно названы. Без аналитики и подключённого SMTP.

## Перенос данных (этап 7)

Инвентаризация контента и версий LMS → резервная копия → таблицы соответствия ID/URL → read-only экспорт в staging → проверка файлов, числа записей и прав → тестовый импорт → сверка владельцами → согласованный запуск с планом отката. Старый LMS остаётся доступным до завершения миграции и приёмки. Никаких destructive-команд к текущим сайтам не выполнено.
